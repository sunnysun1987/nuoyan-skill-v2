# 开发与发布检查清单

本清单适用于诺研 Skill 的代码修改、真实项目回归、本机安装同步和 GitHub 发布。任何一项未完成，不得表述为“已发布并验证”。

## 1. 开始前

- 读取 `git status --short --branch`，确认当前分支、远端差异和未跟踪文件。
- 核对仓库版本、用户级安装目录版本、`nuoyan` 元数据版本和实际导入源码路径。
- 明确问题属于代码缺陷、执行错误、环境限制还是业务证据缺口；不同类别不得互相替代。
- 保留用户已有修改，不把 `runs/`、备份或其他无关文件混入提交。

## 2. 缺陷修复

- 先用最小 bad case 写出失败测试，并确认测试在修复前真实失败。
- 修复必须作用于生成器、状态机或门禁源码，不手工修改单个交付 HTML 代替代码修复。
- 同一任务目录内会写 `task.json`、材料、证据卡或报告的命令必须串行执行；并行只用于互不写同一状态的只读检查。
- 访问失败、权限失败、解析失败和真实无结果必须分开；只要通道未成功，就不能声明 `no_results`。
- “全部证据卡”的数量必须等于底层证据卡总数；排除项保留审计入口，并标记排除原因。
- `delivery_artifacts_ready` 只判断交付文件完整性；证据闭环、人工复核和来源覆盖由其他门禁及 `business_ready` 判断。
- 受限或失败来源必须记录可执行的重试、浏览器、公开来源导入或人工补证动作，但不得因此伪装为来源已闭环。

## 3. 每个独立修改

- 运行对应目标测试、Ruff 和 `git diff --check`。
- 回读关键输出或状态文件，确认写后读结果与命令输出一致。
- 独立本地提交，使用中文提交说明；不要把多类缺陷压成一个不可审计提交。

## 4. 发布前 CI

- `python3 -m pytest -q`
- `ruff check scripts/`
- `python3 -m compileall -q scripts`
- `git diff --check`
- `PYTHONPATH=scripts python3 -m ivd_research.cli doctor --strict --json --output-root <可写验收目录>`
- 核对 `pyproject.toml`、`WORKFLOW_VERSION`、README 和安装测试中的版本一致。
- 核对根目录模板与 Python 包内模板完全一致。

## 5. 真实项目回归

- 用代表性真实任务重新生成标准交付物，不以单元测试替代真实 DOM 和状态回放。
- 核对六个页签、关键计数、筛选属性、排除审计和跳转入口。
- 顺序回读 `task.json`、`manifest.json` 和 `verify-package`，记录各门禁的真实值。
- 明确区分已实现、已验证、仅当前环境验证、尚未覆盖和仍需人工判断。

## 6. 用户级安装验证

- 更新前完整备份 `~/.codex/skills/nuoyan-skill-v2`。
- 从 Git 已提交内容导出安装文件，排除 `.git`、`runs/`、备份和未跟踪文件。
- 同步后核对 Skill、源码、模板和版本文件的哈希或内容一致性。
- 刷新 editable 安装，确认 `importlib.metadata`、实际源码路径和 `pip show` 均指向当前版本。
- 在用户级安装目录重新运行全量测试和严格 doctor。

## 7. GitHub 发布

- 使用与版本一致的发布分支和 `vX.Y.Z` 标签。
- 推送前再次确认工作树只剩明确排除的未跟踪项目数据或备份。
- 只有用户明确授权后执行 push。
- 发布后核对远端分支、标签和提交哈希；CI 未完成前不得宣称远端验证通过。

## 8. Bad Case 记忆

- 每次真实项目发现的新失败模式，记录症状、根因、代码修复、测试、执行约束和残余风险。
- 代码 bad case 写入回归测试；执行 bad case 写入本清单和长期记忆；环境 bad case 写清当前环境边界。
- 下次发布前回看历史 bad case，确认没有重复出现同类错误。
